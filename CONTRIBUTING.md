# Contributing

Thank you for helping improve this portfolio. Keep changes focused on clarity, accessibility, truthful project evidence, maintainability, and performance.

## Before opening a pull request

1. Explain the visitor or maintenance problem the change solves.
2. Keep public content centralized in `src/content/site.ts` where possible.
3. Do not add placeholder URLs, invented metrics, or unverified project ownership.
4. Check keyboard navigation and responsive layouts for UI changes.
5. Run the repository checks:

```bash
npm install
npm run format:check
npm run lint
npm run typecheck
npm run build
```

## Pull request notes

Include a short summary, the files or sections changed, validation performed, and screenshots for visible UI changes. If a change affects deployment metadata, public URLs, résumé assets, or client-project disclosures, call that out explicitly.

## Content standards

Client work must be labeled appropriately. Do not include confidential information. State limitations when a source repository, live demo, or production metric is unavailable. A smaller set of accurate projects is preferred to a larger set of unclear or duplicated work.
